# 06_firehose: consumer を書かないという設計 — バッファリングが生む near-real-time

`05_kinesis.md` までの 4 サービスは、いずれも `apps/` 配下に produce / consume の Go コードを持ち、`make demo-*` で実際に動かしながら学んだ。本ドキュメントの主役である Amazon Data Firehose（2024 年 2 月に Amazon Kinesis Data Firehose から改称。本書では現行名の Data Firehose を用いるが、AWS の API・CLI コマンド名は `firehose` のまま変わっておらず、旧称のドキュメントにはまだ Kinesis の名残がある）には、そもそも書くべき consumer コードが存在しない。この「コードがない」こと自体が本章最後の学習ポイントであり、なぜコードが要らないのかを理解することが本ドキュメントの目的になる。

---

## 1. イントロ — なぜ本章だけハンズオンがないのか

`01_concepts.md` セクション 6 のマッピング表がすでに示した通り、Firehose は SQS / ActiveMQ / Kafka / Kinesis Data Streams と同じ「stream 系」に位置づけながら、唯一 consumer という役割そのものを持たないサービスである。他の 4 サービスは「誰かが producer としてメッセージを送り、誰かが consumer としてポーリングまたは購読して取り出す」という双方向の API を提供する。Firehose が提供するのは片方だけ、すなわち producer 側（データを受け取る入口）である。受け取ったデータをどう配るかは、consumer コードではなく **配送先（destination）の設定** で決まる。S3・Redshift・OpenSearch Service・Splunk や汎用 HTTP endpoint といった宛先へ、Firehose 自身がバッチをまとめて書き込みに行く。利用者はポーリングループも `GetRecords` も書かない。書くのはせいぜい「配送前にレコードをどう変換するか」を定義する Lambda 関数（セクション 4）だけであり、それすら任意である。

したがって本章の環境（README 相当の注意書き）でも、Firehose だけは `docker compose up` で立ち上げてローカルで叩く対象に含めていない。LocalStack の Firehose エミュレーションはできなくはないが、「バッファが溜まって配送される」という本質的な挙動は秒単位のバッファ時間を待つ待ち時間そのものが観察対象であり、モックで再現しても得られる学びが薄い。ローカルで無理に再現するより、**「consumer コードを書かなくていい」という設計上の割り切りを概念として理解する** ほうが本サービスの理解としては本質的である。以降のセクションでは、なぜこの割り切りが成立するのか、その代償は何かを順に見ていく。

代表的な配送先（destination）を挙げると次のようになる。いずれも「宛先固有の書き込み作法」を Firehose が肩代わりする点は共通している。

| 宛先 | 典型用途 |
|------|----------|
| Amazon S3 | データレイクへのアーカイブ、Athena / Redshift Spectrum での後段分析 |
| Amazon Redshift | S3 経由での `COPY` によるロード（内部的には一度 S3 に置いてからロードする） |
| Amazon OpenSearch Service | ログの全文検索・可視化 |
| Splunk / Datadog 等の HTTP endpoint | サードパーティ監視・SIEM 基盤への転送 |

## 2. バッファリングという本質 — near-real-time であって real-time ではない

Firehose の配送は「レコードが届いたら即座に 1 件ずつ宛先へ書き込む」わけではない。内部で一定時間・一定サイズだけレコードを溜め込み、閾値に達した時点でまとめて 1 つのオブジェクト（S3 の場合は 1 ファイル）として書き出す。この閾値は **buffering hints** と呼ばれ、大きく 2 つの軸で構成される。

- **buffer size**: 溜め込むデータ量。宛先が S3 の場合、数 MB 単位で設定できる（下限・上限は宛先やコンソール/API のバージョンによって変わるため本書では具体的な MB 数を断定しない）。
- **buffer interval**: 溜め込む時間。宛先によっては最短 0 秒（実質バッファなし）に設定できるオプションもあるが、典型的には数十秒〜数百秒のオーダーで設定する。よく引き合いに出される「デフォルト感覚」は 5 MB / 300 秒程度だが、これも宛先・設定変更の変遷により変わりうる数字なので、目安として捉えるべきである。

どちらの閾値であれ、**先に到達した方** でバッファがフラッシュされ、配送が実行される。この設計は Firehose の都合というより、**配送先側の都合から逆算した必然** である。たとえば S3 に「1 レコード = 1 ファイル」で書き込んだらどうなるかを考えてみるとよい。秒間数千件のイベントが秒間数千個の極小オブジェクトとして S3 に溜まり、あとから Athena や Redshift Spectrum でスキャンしようとすれば、小さすぎるファイルが大量に存在する「small file problem」でスキャン効率が著しく落ちる。Redshift の `COPY` にしても、1 行だけの INSERT を秒間何千回も発行するのは非効率極まりない。バッファリングは「ある程度まとまったサイズのファイル・バッチを作ってから配送先に渡す」ことで、配送先が本来得意とする書き込み単位に合わせる調整弁として機能している。

この設計の直接の帰結が、Firehose は **near-real-time**（ニアリアルタイム）であって **real-time** ではないという性質である。レコードが Firehose に届いてから宛先で読めるようになるまでに、必ずバッファ時間ぶんの遅延が乗る。秒単位より短いレイテンシが要件になるユースケース（不正検知のアラートを即座に発火させたい、等）には Firehose は原理的に向かない。バッファという緩衝材を挟むことで配送効率と引き換えに、届いてから見えるまでのタイムラグを甘受する設計だと理解しておく必要がある。

バッファをフラッシュして宛先へ書き込みに行った先で失敗することもある。宛先が一時的に応答しない、権限が足りない、といったケースでは Firehose は指定した期間・回数リトライし、それでも届かなければ配送できなかったデータをエラー出力用の S3 プレフィックスへ退避する。`01_concepts.md` セクション 5 で見た「本章の 4 ミドルウェアは実用上いずれも at-least-once」という整理は Firehose にも当てはまり、リトライの結果として宛先側に重複したレコードが着地しうる。consumer コードを書かない Firehose であっても、配信保証の考え方そのものは他の stream 系サービスと地続きである。

## 3. 入力ソース — Direct PUT と Kinesis Data Streams

Firehose にデータを流し込む経路は大きく 2 通りある。

1 つ目は **Direct PUT** で、SDK の `PutRecord` / `PutRecordBatch` API や Kinesis Agent、あるいは CloudWatch Logs のサブスクリプションフィルタなどから直接 Firehose の配信ストリームへ書き込む方式である。producer は Firehose の配信ストリーム名だけを知っていればよく、その先の S3 バケットや Redshift クラスタの詳細を意識する必要はない。

2 つ目は **Kinesis Data Streams をソースにする** 方式である。`05_kinesis.md` で見た KDS のストリームに Firehose を「消費者」として登録すると、Firehose が自動的に shard を読み進めてバッファリングし、宛先へ配送する。この構成は「同じデータを 2 つの目的で使い分ける」定番パターンを実現する。1 つは KCL や Lambda（KDS トリガー）でリアルタイムに処理し、ダッシュボード更新や不正検知のような即時性が要るロジックに使う。もう 1 つは同じストリームを Firehose で読み、S3 に長期保存用のアーカイブとして落とす。前者は秒単位のレイテンシを引き受けてでも今すぐ処理したい系、後者は多少遅れてもよいから安く確実に貯めておきたい系、という役割分担になる。

```
                       ┌── (A) KCL / Lambda コンシューマ ──> リアルタイム処理・ダッシュボード
                       │        (04/05 で見た「読み進み位置は自分で管理」する世界)
producer ──PutRecord──>│
                       │  Kinesis Data Streams: orders
                       │
                       └── (B) Firehose（KDS をソースに設定）
                                  │
                                  │  buffer: size か interval、先に到達した方でフラッシュ
                                  ▼
                           S3（Parquet 変換 / 動的パーティショニング）
                                  │
                          （Redshift・OpenSearch・HTTP endpoint への配送も同型）
```

Direct PUT の場合はこの図の (A) が存在せず、producer から Firehose へ直接矢印が伸びるだけの単純な形になる。どちらの経路でも、Firehose から先（バッファリングして宛先へ書き込む部分）の挙動は変わらない。

## 4. 変換と整形 — Lambda 変換・フォーマット変換・動的パーティショニング

Firehose は「受け取ったデータをそのまま右から左へ流す」だけではなく、配送前に加工する仕組みをいくつか持つ。

- **Lambda 変換**: 配信ストリームに Lambda 関数を紐づけると、Firehose はバッファ前の各レコード（バッチ単位）をその Lambda に渡し、戻り値を配送対象として使う。圧縮解凍、JSON の整形、不要フィールドの除去、フォーマットの正規化といった前処理を挟める。レコードごとに成功・失敗のステータスを返す必要があり、失敗したレコードは指定した S3 プレフィックスへ退避される。
- **フォーマット変換（Parquet / ORC）**: 宛先が S3 の場合に限り、JSON レコードを列指向フォーマットである Parquet や ORC に変換してから書き込める。Athena や Redshift Spectrum で後から分析するときに、列指向フォーマットは読み込むカラムだけをスキャンできるためコストとレイテンシの両面で有利になる。変換には AWS Glue Data Catalog に登録したテーブル定義（スキーマ）を使う。
- **動的パーティショニング（dynamic partitioning）**: レコードの中身（JSON のフィールド値など）を見て、S3 の書き込み先プレフィックスを動的に変える機能である。たとえば `customer_id` や `event_type` といったフィールド値ごとにプレフィックスを分けて `s3://bucket/event_type=order/...` のように配置すれば、Athena 側でパーティションプルーニングが効き、スキャン対象を絞り込める。動的パーティショニングを有効にすると、同じプレフィックスにまとまるレコードが出そろうまでバッファを長めに持つ必要が出てくるため、buffer hints とのトレードオフも意識することになる。

これらはいずれも「consumer が受け取ってから加工する」のではなく、「Firehose が配送する直前に加工する」という位置づけである点が重要である。consumer コードが存在しない代わりに、変換ロジックは Firehose の設定（またはそこから呼ばれる Lambda）の中に押し込まれる。

## 5. Kinesis Data Streams との使い分け

`05_kinesis.md` で見た KDS と Firehose は、同じ「stream から配る」系統でありながら、利用者に残す自由度がまったく違う。両者の対応を整理すると次のようになる。

| 観点 | Kinesis Data Streams | Firehose |
|------|----------------------|----------|
| consumer コード | 自分で書く（KCL / `GetRecords`） | 存在しない（宛先設定のみ） |
| レイテンシ | 秒未満〜数秒 | near-real-time（バッファ時間ぶん遅延） |
| スケール単位 | shard（自分で管理 or オンデマンド） | Firehose 側が自動でスケール、shard 相当の概念を意識しない |
| 配送先 | 任意（consumer が自由に実装） | S3 / Redshift / OpenSearch / HTTP endpoint 等の定番メニュー |
| 課金 | shard 時間 or GB（オンデマンド） | 取り込みデータ量（GB）ベース |
| リプレイ | 可能（保持期間内でオフセットを巻き戻す） | 不可（Firehose 自体はデータを保持しない通過点） |

判断基準を要約すると、**自分でコンシューマを書きたい／複数系に配りたい／秒単位のレイテンシが要る → KDS**。KCL や独自の `GetRecords` ループを書き、shard iterator や checkpoint を自分で管理する代わりに、処理内容もタイミングも自由に設計できる。同じストリームに複数のコンシューマグループをぶら下げて fan-out することもできる。一方、**決まった配送先へ、決まった形式で流し込むだけでよい → Firehose**。S3 や Redshift のような定番の宛先へ「貯めて置く」だけなら、consumer の実装・デプロイ・監視・スケーリングを丸ごと引き受けてもらえる。

この違いは、結局のところ **何を対価に何を得るか** という一点に集約される。Firehose は shard 管理も consumer プロセスの運用も要らず、GB あたりの従量課金だけで済む（自動でスループットに追従してスケールする）。その代償として、バッファリングによるレイテンシの上乗せと、宛先が固定メニューの範囲に限られるという柔軟性の欠如を引き受けている。逆に KDS は shard 単位のスループット管理や consumer プロセスの運用負担を利用者側が背負う代わりに、秒単位のレイテンシと自由な配送ロジックを手に入れる。「consumer 開発・運用コストをゼロにする」という Firehose の売り文句は、裏を返せば「その分の意思決定と柔軟性を手放す」という取引でもある。どちらが正しいかはユースケース次第であり、この判断軸は `07_selection_guide.md` で他サービスとの比較に組み込んで扱う。

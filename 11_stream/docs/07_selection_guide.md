# 07_selection_guide: 5 サービスをどう選ぶか — 料金・要件・乗り換え目安

`01_concepts.md` から `06_firehose.md` まで、SQS / ActiveMQ / Kafka / Kinesis Data Streams / Firehose の 5 サービスを queue と stream という 2 つのデータモデルに分けて、それぞれの設計と挙動を手を動かしながら見てきた。本ドキュメントはその総まとめとして、「結局どれをいつ選ぶのか」「安く見えたサービスが、どの流量でどのサービスに逆転されるのか」を、**東京リージョン（ap-northeast-1）の実単価に基づく月額試算**から導く。各サービスの機能そのものの説明は 02〜06 に譲り、ここではそれらを選定の意思決定に落とし込むことに集中する。

料金は変動するため、本書の数字は **執筆日 2026-07-10 時点** の ap-northeast-1 単価であることを最初に明記しておく。単価は各サービスの公式料金ページと、それを機械可読にした AWS Price List Bulk API（`pricing.us-east-1.amazonaws.com`、リージョン `ap-northeast-1`）の両方で 2026-07-10 に照合した値を用いる。出典 URL はセクション 3 の単価表に付す。

## 1. 選定ディシジョンツリー

まず「そもそも queue なのか stream なのか」から入る。`01_concepts.md` セクション 4 の「配って消す queue / 追記して残す stream」という軸が、そのまま最初の分岐になる。

```
このデータは何か？
│
├─ 完了したら消えてよい「仕事（ジョブ／タスク）」を 1 人のワーカーに配りたい
│   → queue
│   ├─ AWS 内で完結してよい・運用を持ちたくない
│   │     → SQS（standard。順序が要れば FIFO）
│   └─ 標準プロトコル(STOMP/AMQP/JMS)が要る・オンプレ資産を引き継ぐ・topic fan-out が要る
│         → ActiveMQ（マネージドにするなら Amazon MQ）
│
└─ 「イベントの記録」を複数系が読む／後から参加した系も過去を読む／リプレイが要る
    → stream
    ├─ 消費側コードを書きたくない・決まった宛先(S3/Redshift/OpenSearch)へ流すだけ
    │     → Firehose（near-real-time で可・秒未満レイテンシは不可）
    ├─ 消費側を自分で書く・秒単位レイテンシ・複数コンシューマグループが要る
    │     → Kinesis Data Streams
    │       （立ち上げ期・流量が読めない → オンデマンド／定常化 → プロビジョンド）
    └─ 上記に加えて高スループット定常運用・Kafka エコシステム(Connect/Streams)が要る
          → Kafka（セルフホスト or Amazon MSK）
```

このツリーは「安い順」でも「高機能順」でもなく、**要件の分岐**で並んでいる。料金はこの後のセクションで別軸として重ねる。要件上は複数の選択肢が残ることが多く、そこで初めて「では月額はいくら違うのか」が効いてくる。

## 2. 機能比較マトリクス

02〜06 で確認した事実を 1 枚に集約する。各セルの根拠は該当ドキュメントにある。

| 観点 | SQS | ActiveMQ (Amazon MQ) | Kafka (MSK) | Kinesis Data Streams | Firehose |
|------|-----|----------------------|-------------|----------------------|----------|
| データモデル | queue（配って消す） | queue + topic | stream（追記ログ） | stream（追記ログ） | stream 配送（通過点） |
| 順序保証 | standard 無 / FIFO は group 単位 | 単一consumerなら送信順 | partition(key)単位 | shard(partition key)単位 | 保証しない（配送のみ） |
| リプレイ | 不可 | 不可 | 可（offset 巻き戻し） | 可（保持期間内 iterator） | 不可（保持しない） |
| fan-out 方式 | 単体では不可（+SNS） | topic 購読（接続中のみ） | consumer group を分ける | shard を複数 group が読む | 不可（1宛先へ配送） |
| 保持期間 | 最大 14 日（消費で消滅） | 消費で消滅（永続はディスク次第） | retention 設定（実質無制限可） | 24h 既定〜365d | 保持しない |
| スループット上限 | 実質無制限（AWS がスケール） | 単一ブローカーの CPU/IO に律速 | broker 増設でスケール | shard 数ぶん（1MB/s・1000rec/s per shard） | 自動スケール |
| 運用負荷 | ほぼゼロ（フルマネージド） | 高（自前運用）/中（Amazon MQ） | 高（rebalance・retention 容量管理） | 中（shard/reshard・KCL） | ほぼゼロ（宛先設定のみ） |
| レイテンシ | 数十ms〜（long polling 次第） | 数ms〜 | 数ms〜秒 | 秒未満〜数秒 | near-real-time（バッファ時間） |
| プロトコル可搬性 | AWS 独自 HTTPS API | STOMP/AMQP/OpenWire/MQTT | Kafka プロトコル（広範なエコシステム） | AWS 独自 API | AWS 独自（入口のみ） |

読み方の勘所は 3 つある。第 1 に、**リプレイと group 単位 fan-out は stream の専売**であり、SQS/ActiveMQ の queue では原理的に持てない（`04_kafka.md` セクション 4）。第 2 に、**運用負荷とスループット上限はトレードオフ**で、フルマネージドな SQS/Firehose は運用ゼロだが挙動の自由度が低く、Kafka は自由度と引き換えに rebalance・retention 容量管理という重い運用を背負う（`04_kafka.md` セクション 6）。第 3 に、**Firehose だけは「配送の通過点」**であり、他 4 サービスと違って自分でデータを保持・リプレイする対象ではない（`06_firehose.md` セクション 5）。

## 3. 料金構造の違い — 何に課金されるか

料金比較で最初に押さえるべきは「金額の大小」ではなく「**何に対して課金されるか**（課金軸）」である。課金軸が違えば、同じ流量でも安いサービスと高いサービスが入れ替わる。

| サービス | 課金軸 | 月額の式 |
|---|---|---|
| SQS standard | リクエスト数 | (send + receive + delete のリクエスト数 ÷ 100万) × 単価 ※ペイロード 64KB ごとに 1 リクエスト単位 |
| Amazon MQ | ブローカー常駐時間 | インスタンス時間 × 730h × 単価 + ストレージ(GB-月) |
| KDS プロビジョンド | shard 時間 + PUT | shard 数 × 730h × 単価 + PUT ペイロードユニット(25KB)数 × 単価 |
| KDS オンデマンド | データ量 | ストリーム時間 × 730h × 単価 + 取込 GB × 単価 + 読出 GB × 単価 |
| Firehose | 取込データ量 | 取込 GB × 単価 ※レコードは 5KB に切り上げて課金 |
| MSK | broker 常駐時間 | broker 数 × 730h × 単価 + ストレージ(GB-月) |

この表から読み取るべき性質は次の通り。**SQS は「回数」課金**なので、1 通が小さくても回数が多ければ高くなる。**MQ / MSK は「時間」課金**なので、流量がゼロでもブローカーが立っている限り定額が発生する。**KDS プロビジョンドは「器（shard）＋回数（PUT）」の折衷**、**KDS オンデマンドと Firehose は「データ量（GB）」課金**で流量に素直に比例する。

## 4. シナリオ試算表

**前提**（すべての列に共通）:

- **1 レコード = 1KB**、**24 時間 × 365 日の定常流量**、**コンシューマは 1 系統**。
- 月間データ量 = 流量(MB/s) × 2,592,000 秒（= 30 日）。インスタンス／shard 時間課金は 730h/月。GB は 10 進（1GB = 1000MB = 10^6KB）で統一する。この換算だと 1KB レコードでは **流量 1 MB/s = 1,000 レコード/s** となり、KDS の「1 shard = 1MB/s または 1,000 rec/s」の 2 つの上限がちょうど一致する。
- KDS プロビジョンドの必要 shard 数は次式で決まる（`05_kinesis.md` セクション 2 の per-shard 制約から）:

  ```
  shards = max( ceil(write MB/s ÷ 1), ceil(records/s ÷ 1000), ceil(read MB/s ÷ 2) )
  ```

  1KB レコード・コンシューマ 1 系統では write と records/s が同値、read(2MB/s per shard) は 1 消費なら余裕があるため、`shards = 流量(MB/s)` になる（1 → 1、10 → 10、50 → 50）。

**月額試算（USD、ap-northeast-1、2026-07-10 単価）**:

| サービス | 1 MB/s | 10 MB/s | 50 MB/s |
|---|--:|--:|--:|
| SQS standard | $3,110 | $31,104 | $155,520 ※ |
| Amazon MQ（単一 m5.large） | $272 | $272 | $272 †|
| KDS プロビジョンド | **$70** | $700 | $3,498 |
| KDS オンデマンド | $442 | $4,081 | $20,256 |
| Firehose | $467 | $4,666 | $23,328 ‡ |
| MSK（3 broker m5.large） | $604 | **$697** | **$1,112** |

太字は各流量での最安。**1 MB/s では KDS プロビジョンドが最安、10 MB/s と 50 MB/s では MSK が最安**に入れ替わる。この入れ替わりこそがセクション 5 の乗り換え目安の核心である。

### 各セルの計算過程（単価を代入した形）

**SQS standard**（send + receive + delete = 3 リクエスト/通、1KB < 64KB なので 1 通 = 1 リクエスト単位、バッチ未使用）:
- レコード数/月 = 流量 × 1,000 rec/s × 2,592,000s。1 MB/s なら 2.592×10⁹ 通。
- リクエスト数 = 3 × レコード数。1 MB/s: 7.776×10⁹、10 MB/s: 7.776×10¹⁰、50 MB/s: 3.888×10¹¹。
- 1 MB/s: 7.776×10⁹ × $0.0000004 = **$3,110**／10 MB/s: ×10 = **$31,104**／50 MB/s: 3.888×10¹¹ × $0.0000004 = **$155,520**。
- ※ 50 MB/s はリクエスト数が 100億超のため逓減価格が入る。厳密には (100億×$0.40 + 100億×$0.35 + 188.8億×$0.32)/100万 = **$135,416**。桁の結論は変わらない。バッチ API（send/receive/delete とも最大 10 件/呼び出し）を使えば理論上 1/10 に下げられる。

**Amazon MQ（単一 mq.m5.large ActiveMQ）**:
- $0.372/時間 × 730h = **$271.56 ≈ $272**。流量に依存しない定額（+ ストレージ、ドレインされる queue なら 5GB 無料枠内でほぼ加算なし）。
- † 単一 m5.large は 10〜50 MB/s の実スループットを 1 台で捌けない。表の $272 は「流量ゼロでも定額が立つ」という課金軸を示す下限であり、実際にその流量を出すにはインスタンス増強・クラスタ化が要り、定額の床がさらに上がる。

**KDS プロビジョンド**（shard 時間 + PUT ユニット。読出は shard 料金に含まれ無料）:
- shard 数 = 流量（1 / 10 / 50）。shard 料金 = shard 数 × 730h × $0.0195。
- PUT ユニット = レコード数（1KB → 1 ユニット）。PUT 料金 = レコード数 × $0.0000000215。
- 1 MB/s: (1 × 730 × $0.0195) + (2.592×10⁹ × $0.0000000215) = $14.24 + $55.73 = **$69.96 ≈ $70**。
- 10 MB/s: $142.35 + $557.28 = **$700**／50 MB/s: $711.75 + $2,786.40 = **$3,498**。

**KDS オンデマンド**（ストリーム時間 + 取込 GB + 読出 GB）:
- ストリーム時間 = $0.052 × 730h = $37.96（定額）。取込 GB = 流量 × 2,592。読出 GB = 同量（1 消費）。
- 1 MB/s: $37.96 + (2,592 × $0.104) + (2,592 × $0.052) = $37.96 + $269.57 + $134.78 = **$442**。
- 10 MB/s: $37.96 + $2,695.68 + $1,347.84 = **$4,081**／50 MB/s: $37.96 + $13,478.40 + $6,739.20 = **$20,256**。

**Firehose**（取込 GB、1KB レコードは 5KB に切り上げ → 課金バイトは実データの 5 倍）:
- 課金 GB = レコード数 × 5KB ÷ 10⁶ = 流量 × 12,960 GB。
- 1 MB/s: 12,960 × $0.036 = **$467**／10 MB/s: 129,600 × $0.036 = **$4,666**／50 MB/s: 648,000 × $0.036 = **$23,328**。
- ‡ 50 MB/s の課金量 648TB は 512TB を超えるため一部が Tier2($0.031)。厳密には 512,000×$0.036 + 136,000×$0.031 = **$22,648**。

**MSK（3 broker kafka.m5.large、保持 24h で KDS 既定と揃える）**:
- broker 料金 = 3 × $0.271 × 730h = $593.49（定額の床）。ストレージ = 流量 × 86.4GB（24h 分）× $0.12/GB-月。
- 1 MB/s: $593.49 + (86.4 × $0.12) = $593.49 + $10.37 = **$604**。
- 10 MB/s: $593.49 + $103.68 = **$697**／50 MB/s: $593.49 + $518.40 = **$1,112**。

### 検算（1 MB/s 列）

- SQS: 1,000 rec/s × 2,592,000s = 2.592×10⁹ 通 → ×3 = 7.776×10⁹ req → ×4×10⁻⁷ = **$3,110.40**。桁: 10⁹ × 10⁻⁷ = 10²、×7.776×4 ≒ 3.1×10³。✓
- KDS プロビジョンド PUT: 2.592×10⁹ ユニット × 2.15×10⁻⁸ = 5.5728×10¹ = **$55.73**。shard $14.24 と合わせ **$69.96**。✓
- Firehose: 2.592×10⁹ 通 × 5KB = 1.296×10¹⁰ KB = 12,960 GB × $0.036 = **$466.56**。✓
- MSK broker: 3 × 0.271 × 730 = **$593.49**。✓

表から読み取れる 3 つの事実:（1）**SQS は stream 的流量では桁違いに高い**（1 MB/s で KDS プロビジョンドの約 44 倍）。（2）**MQ / MSK は流量ゼロでも定額の床が立つ**（MQ $272、MSK $604）が、その代わり高流量では床が効いて割安になる。（3）**Firehose は 1KB レコードでは 5KB 切り上げの罰則で KDS プロビジョンドの約 6.7 倍**になり、「GB 課金 = 安い」という直感が小レコードでは成立しない。

## 5. 乗り換え目安

ここが本章の核心である。上の試算の実数から、どの流量・要件でサービスを乗り換えるべきかを導く。

### Firehose → KDS

まず料金面。試算の通り、**1KB レコードでは Firehose（流量あたり約 $467/MB·月）は KDS プロビジョンド（約 $70/MB·月）より一貫して高い**。両者とも流量にほぼ比例するため、「◯ MB/s を超えたら KDS が安くなる」という流量のクロスポイントは**存在しない**（比が流量に依らず一定）。効くのは流量ではなく **レコードサイズ**である。Firehose は 5KB 未満を 5KB に切り上げるため、1KB のような小レコードでは実データの 5 倍を課金され、KDS との差が最大化する。逆に 1 レコードが 5KB 以上あれば切り上げの罰則が消え、Firehose は実 GB（1 MB/s で 2,592GB → $93/月）まで下がるが、それでも KDS プロビジョンド（同条件で $25〜70/月）よりは高い。つまり**純粋なサービス料金では Firehose は基本的に KDS より高く、Firehose を選ぶのは「コンシューマを一切書かない／運用しない」という運用コスト削減の対価**である（KDS は別途コンシューマの計算資源が要る点は本試算に含めていない）。

したがって Firehose → KDS の乗り換えは料金クロスではなく **要件クロス**で起きる:
- **秒未満のレイテンシが要る**: Firehose はバッファ時間ぶんの near-real-time が原理的な下限（`06_firehose.md` セクション 2）。不正検知の即時発火などには KDS。
- **消費系が 2 つ以上になった**: Firehose は 1 宛先へ配送するだけ。複数系が独立に読む／リプレイするなら KDS の shard を複数 group で読む。
- **変換が Lambda で収まらない**: Firehose の加工は Lambda 変換・フォーマット変換・動的パーティショニングの枠（`06_firehose.md` セクション 4）。それを超える処理は自前コンシューマ＝KDS。
- **小レコードで取込量が膨らんだ**: 上記の 5KB 切り上げで Firehose の請求が跳ねる場合、料金面からも KDS が正当化される。

### KDS → MSK / Kafka

ここには**明確な流量クロスポイントがある**。KDS プロビジョンドは shard を積み上げるほど費用が線形に増える（流量あたり約 $70/月）のに対し、MSK は最小 3 broker の**定額の床（$593.49/月）＋わずかなストレージ**で、流量が増えても床の上に緩やかに乗るだけである。両者が交わる点は:

```
KDS プロビジョンド = MSK
70.0 × R  =  593.49 + 10.37 × R     （R = 流量 MB/s、MSK は保持 24h のストレージ込み）
59.6 × R  =  593.49
R ≈ 10 MB/s
```

試算表がこれを裏付ける: **1 MB/s では KDS $70 ≪ MSK $604、10 MB/s では KDS $700 ≒ MSK $697 でほぼ拮抗、50 MB/s では KDS $3,498 ≫ MSK $1,112 と MSK が 3 倍以上安い**。つまり **概ね 10 MB/s を境に、それ以上の定常流量では MSK（Kafka）の定額床が償却されて有利になる**。

料金以外の制約分岐も同方向に働く:
- **GetRecords 5 回/秒 per shard の壁**（`05_kinesis.md` セクション 2）がレイテンシ要件と衝突する。Enhanced Fan-Out は追加課金。Kafka にこの種の pull 回数上限はない。
- **shard 上限・reshard 運用が痛い**: 流量変動のたびに split/merge を判断・実行する運用（`05_kinesis.md` セクション 4）が重くなったら、partition 増設で捌く Kafka が視野に入る。
- **Kafka エコシステムが欲しい**: Kafka Connect（各種コネクタ）や Kafka Streams（ストリーム処理）といった資産を使いたいなら KDS では代替できず、MSK / セルフホスト Kafka になる。

### SQS → stream 系

SQS は queue なので本来「消して終わり」のジョブ配布向きだが、**イベントを高頻度で流し続ける stream 的な使い方をするとリクエスト課金が破綻する**。試算の通り、1 MB/s（= 2.6×10⁹ 通/月）で既に**月 $3,110**（バッチ未使用）、10 MB/s で $31,104、50 MB/s で $13.5〜15.5 万に達する。同じ流量の KDS プロビジョンド（$70 / $700 / $3,498）と比べ、桁が 1〜2 つ違う。

乗り換えの合図は 2 つが重なったときである:（1）**リクエスト課金の月額が同流量の stream 系（KDS プロビジョンド）を明らかに上回った** — 目安として数千 rec/s の定常が続けば SQS の請求は stream の数十倍になる。（2）**fan-out（複数系が同じイベントを読む）やリプレイ（過去イベントの読み直し）の要件が出た** — これは SQS では単体で満たせず（`03_activemq.md` の topic か SNS の併用が要る）、stream に移る本質的な理由になる。逆に言えば、**要件が「1 通を 1 ワーカーが処理して消す」ままなら、多少割高でも SQS の運用ゼロが勝つ**ことも多い。

### 逆方向 — 過剰スペックの引き下げ

乗り換えは高機能側への一方通行ではない。**Kafka / MSK を立てたが、実は fan-out もリプレイも使っておらず、単に「1 通を 1 ワーカーで処理」していただけ**というケースは珍しくない。この場合、rebalance・retention 容量管理・broker 監視という Kafka 固有の運用負荷（`04_kafka.md` セクション 6）と MSK の定額床（月 $600〜）を払い続ける意味がなく、**SQS へ引き下げれば運用ゼロかつ低流量なら安い**。同様に、**KDS をオンデマンドのまま定常運用している**なら、試算の通りオンデマンドはプロビジョンドの約 6 倍（1 MB/s で $442 vs $70）なので、流量が読めてきた段階でプロビジョンドへ引き下げる（`05_kinesis.md` セクション 4 の「最初はオンデマンド、定常化したらプロビジョンド」）。「上げる」判断と同じ熱量で「下げる」判断もする、というのが料金最適化の実務である。

## 6. 移行時の注意

サービスを乗り換えると決めても、データの付け替えだけでは済まない。以下は移行の前提条件として設計に織り込む必要がある。

- **API 非互換で SDK 層の書き換えが必須**: SQS・KDS・Firehose はいずれも AWS 独自 API、Kafka は Kafka プロトコル、ActiveMQ は STOMP/AMQP と、ワイヤプロトコルが互換でない（`03_activemq.md` セクション 3）。producer / consumer のコードは「送る・受ける」の骨格から書き直しになる。抽象化レイヤを噛ませていないと影響範囲が広がる。
- **デュアルライト期間を設ける**: 一気に切り替えず、一定期間は新旧両方へ書き込み（dual-write）、新経路の消費が正しいことを検証してから旧経路を止める。切替手順は「新経路 consumer 稼働 → producer を dual-write 化 → 新経路の整合を確認 → producer を新経路のみに → 旧経路を drain して停止」の順が基本。
- **オフセット / シーケンス番号は移行先に引き継げない**: Kafka の offset、Kinesis の sequence number、SQS の receipt handle はいずれもサービス固有で、移行先の位置管理へそのまま持ち込めない。「どこまで処理したか」を移行先の採番で数え直すことになるため、**移行中に同じイベントが新旧両経路から二重に届くのは前提**であり、コンシューマの冪等性（`01_concepts.md` セクション 5）が移行を安全に行える前提条件になる。
- **順序保証の粒度が変わる**: 順序を寄せるキーの呼び名と粒度がサービスごとに違う — SQS FIFO は `MessageGroupId`、Kafka は record key、Kinesis は partition key。移行前後で「どの単位の順序が保たれるか」がずれないよう、キー設計を対応付けて確認する。

## 7. スコープ外のサービスへの言及

本章は 5 サービスに絞ったが、実務で隣接して名前が挙がる 3 つに一言ずつ触れておく。いずれも本ハンズオンの対象外である。

- **RabbitMQ**: AMQP を中心とした broker 型 MQ で、ActiveMQ と同じ「自前 or Amazon MQ でマネージド」の queue 系列に入る。柔軟な routing（exchange/binding）が強みで、ActiveMQ の代替として Amazon MQ が RabbitMQ エンジンも提供する（セクション 3 の単価表にも RabbitMQ 行が存在する）。選定軸は ActiveMQ とほぼ同じ「標準プロトコル・topic/routing・セルフ運用可搬性」なので、本章の queue 側の議論がそのまま応用できる。
- **SNS（Simple Notification Service）**: pub/sub 型の**通知**サービスで、それ自体は保持もリプレイもしない。SQS が単体で持てない fan-out を補うために「SNS → 複数 SQS」の組み合わせ（fan-out パターン）で頻出する。本章の「fan-out が要るなら stream」という結論に対する、queue 側での fan-out の実装手段として位置づけられる。
- **EventBridge**: イベントの内容でルーティングする**イベントバス**で、多数の AWS サービスや SaaS を疎に繋ぐ用途に向く。ルールベースのフィルタリングとターゲット振り分けが主眼で、高スループットの生ストリーム処理（KDS/Kafka の領域）とは狙いが異なる。「マイクロサービス間をイベントで疎結合したい」という `01_concepts.md` セクション 2 のイベント駆動の目的に、本章のストリームとは別のアプローチで応えるサービスである。

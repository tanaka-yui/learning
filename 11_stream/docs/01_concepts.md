# 01_concepts: 非同期メッセージングの全体像

本章では「注文を受け付けたら、その後の処理を別系統に委ねる」非同期メッセージングを、queue（SQS / ActiveMQ）と stream（Kafka / Kinesis）という 2 つの系統に分けて 4 つの Go ハンズオンで学ぶ。この最初のドキュメントでは、まず同期処理の限界から出発し、なぜ非同期にするのか、そして queue と stream が本質的に何を違えているのかという「章全体の軸」を整理する。個別ミドルウェアのコードウォークスルーは `02` 以降に譲り、ここでは全体を貫く用語（queue / stream・at-least-once・冪等性・fan-out）を定義する。

---

## 1. イントロ — 同期処理の限界

Web アプリケーションが注文リクエストを受け取り、その HTTP ハンドラの中で「確認メールの送信」「在庫データベースの更新」「分析基盤へのログ送信」を順番に呼び出すコードを考える。書き味としては素直で、注文が確定した時点ですべての後続処理が終わっているという安心感もある。しかしこの設計には 2 つの構造的な弱点がある。

1 つ目は **レスポンスタイムが最も遅い処理に律速される** ことである。メール送信の SMTP がたまたま 3 秒かかれば、注文 API のレスポンスも 3 秒かかる。ユーザーにとって「注文を受け付けた」という事実は在庫更新やメール送信より遥かに早く確定できるはずなのに、全処理を直列で待たされてしまう。2 つ目は **下流の障害が注文受付そのものを止める** ことである。分析基盤がメンテナンスで落ちていると、分析ログ送信が例外を投げ、その例外がハンドラ全体を巻き込んで注文が失敗する。本来は無関係なはずの分析系の不調が、事業の根幹である注文受付を道連れにするのは望ましくない。

この「呼び出し元と呼び出し先が時間的にも障害的にも固く結合している」状態を切り離すのが非同期メッセージングである。注文ハンドラは「注文を受け付けた」というメッセージをブローカー（queue / stream）に 1 通置くだけにし、メール・在庫・分析はそのメッセージを各自のペースで拾って処理する。呼び出し元はメッセージを置いた瞬間に応答を返せるようになり、下流が落ちていてもメッセージはブローカーに溜まって待つだけで、注文受付は止まらない。

## 2. 非同期化の 5 つの目的

非同期にする動機は「速くなるから」だけではない。実務では次の 5 つの目的が単独あるいは複合で現れる。それぞれ本章で扱う具体例を 1 つずつ添える。

- **デカップリング（障害の分離）**: 送信側と受信側の生存を切り離す。分析基盤が落ちていても、注文イベントは queue / stream に積まれて待つだけで、注文受付 API は 200 を返し続けられる。障害の波及を境界で食い止めるのが第一の目的である。
- **負荷平準化（スパイクをバッファで吸収）**: セール開始直後のように注文が瞬間的に殺到しても、ブローカーがバッファとして受け止め、ワーカーは自分の処理能力の範囲で一定レートで消費できる。ピークに合わせてワーカーを常時過剰配備しなくて済む。
- **ジョブオフロード（重い処理を後ろへ）**: 画像変換やサムネイル生成のような重く時間のかかる処理をリクエストの同期パスから外し、「変換せよ」というジョブメッセージだけを queue に積んでワーカーに任せる。ユーザーには即座に「受付完了」を返せる。
- **fan-out（1 イベントを複数系へ配る）**: 「注文が確定した」という 1 つのイベントを、在庫引当・分析集計・顧客通知という複数の独立した系へ同時に配る。送信側はイベントを 1 回発行するだけで、受信側が何系統あるかを知らなくてよい。
- **イベント駆動（状態変化の通知で系を繋ぐ）**: マイクロサービス間を同期 API 呼び出しの網ではなく「状態が変わった」というイベントの流れで疎に繋ぐ。サービス A の状態変化をサービス B が購読して反応する、という連携をブローカー経由で組む。

これらは排他的ではない。1 つの注文イベントを stream に流す設計は、デカップリング・負荷平準化・fan-out・イベント駆動を同時に満たすことが多い。逆に「重い画像変換を後ろに回したいだけ」なら単純な queue で十分であり、目的に対して過剰な仕組みを選ばないことが設計の勘所になる。

目的とデータモデルの相性にも傾向がある。ジョブオフロードと負荷平準化は「1 通を 1 人のワーカーが処理して終わり」という性質が強く、消したら消える queue が素直に嵌まる。一方で fan-out とイベント駆動は「同じイベントを複数系が、しかも後から参加した系も含めて読みたい」という要求になりやすく、追記ログとして残る stream が向く。デカップリングはどちらでも達成できる横断的な目的である。この「目的 → データモデル」の対応こそが、次のセクションで扱う queue と stream の本質差に直結する。

## 3. 非同期にすべきでないケース

非同期化は万能ではなく、向かない場面がはっきりある。次のようなケースではむしろ同期のまま素直に呼ぶべきである。

- **即時応答が必要**: 残高照会のように「今この瞬間の正しい値を、今すぐ返す」ことが要件なら、メッセージを置いて後で処理する非同期は根本的に噛み合わない。
- **強整合が必要**: 在庫の確定引当のように「二重に引き当ててはならない」処理は、その場でトランザクションを張って結果を確定させたい。結果整合を許す非同期パスに乗せると、二重引当や超過販売のリスク管理が一気に複雑化する。
- **単純な 1:1 の同期 RPC で足りる**: 呼び出し先が 1 つで、結果をすぐ使い、障害も許容できないなら、ブローカーを挟む意味は薄い。運用対象を 1 つ増やすコストのほうが上回る。

そして最も重要な原則は、**非同期にした瞬間、結果整合・重複・順序という 3 つの複雑さを引き受ける** という事実である。この 3 つはそれぞれ次のような形で顔を出す。

- **結果整合（eventual consistency）**: メッセージがいつ処理されるかは分からない。注文直後に在庫画面を見ても、まだ在庫更新メッセージが処理されておらず古い値が見える、という遅延が原理的に生じる。UI 側で「反映まで少し待つ」前提を持つか、確定が必要な箇所は同期で読むといった割り切りが要る。
- **重複（duplicate delivery）**: 同じメッセージが 2 回以上届きうる。後述のとおり本章の 4 ミドルウェアは実用上すべて at-least-once であり、再送は例外ではなく前提である。対策はコンシューマの冪等化（セクション 5）。
- **順序（ordering）**: 送った順に処理される保証は自明ではない。並列ワーカーや複数 partition / shard に分散すると、キー単位の順序が崩れうる。順序が要るなら partition key / message group を揃えて同一パーティションに寄せる、といった設計が必要になる。

この 3 つに向き合う覚悟がないまま非同期化すると、目に見えないデータ不整合を後から追いかけることになる。次章以降のデモは、まさにこの 3 つがコードのどこに現れるかを手で確かめるためのものである。

## 4. queue と stream の本質差（本章の軸）

本章が 4 つのミドルウェアを SQS / ActiveMQ と Kafka / Kinesis の 2 群に分けるのは、この 2 群が **queue** と **stream** という異なるデータモデルに立っているからである。両者の差を以下の観点で整理する。

| 観点 | queue（SQS / ActiveMQ） | stream（Kafka / Kinesis） |
|------|-------------------------|---------------------------|
| データの寿命 | 消費（ACK / 削除）したら消える | 保持期間まで残る追記ログ |
| 読み手の位置管理 | ブローカーが未配信を管理 | コンシューマがオフセットを管理 |
| 複数コンシューマ | 競合（1 通は誰か 1 人が取る） | group ごとに独立して全件読める |
| リプレイ | 不可（消えたら終わり） | 可能（オフセットを巻き戻す） |
| 典型用途 | ジョブ配布・タスクキュー | イベントログ・ストリーム分析・複数系配信 |

この 2 群の消費のされ方の違いを図にすると次のようになる。

```
queue（配って消す）:
  producer ──> [ m1 m2 m3 ] ──> worker A が m1 を取得・ACK ──> m1 は消滅
                    │                worker B は m2 を取得（1 通は誰か 1 人＝競合）
                    └ ブローカーが「まだ配っていないメッセージ」を管理

stream（追記して残す）:
  producer ──> [ m1 m2 m3 m4 ... ]   ← 追記ログ（保持期間まで消えない）
                 ^          ^
                 |          └ group-B offset=3（分析系）
                 └ group-A offset=1（在庫系）
                   各 group が自分の offset を持ち、独立に全件読める／巻き戻せる
```

**queue は「配って消す」モデル** である。ブローカーがどのメッセージをまだ配っていないかを管理し、あるコンシューマがメッセージを取って ACK（SQS なら削除）すると、そのメッセージは消える。複数のワーカーがぶら下がっていても 1 通のメッセージを取るのは誰か 1 人だけ（競合コンシューマ）であり、これがジョブを N 台のワーカーに分散させるのに向く理由である。SQS の消費ループでは、削除するかどうかを `--no-delete` フラグ（[apps/sqs/consumer.go:16](../apps/sqs/consumer.go#L16)）で切り替え、削除の実行を [apps/sqs/consumer.go:47](../apps/sqs/consumer.go#L47) のガードで制御している。基本の「積んで取り出して消す」流れは `make demo-sqs` で試せる。`--no-delete` を付けると ACK されないため、可視性タイムアウト経過後に同じメッセージが再配信される様子を観察でき、これはセクション 5 の `make demo-sqs-dlq` で確認できる。

**stream は「追記して残す」モデル** である。メッセージ（レコード）は消費されても消えず、保持期間が来るまでログに残り続ける。「どこまで読んだか」を管理するのはブローカーではなくコンシューマ側のオフセットであり、Kafka では consumer group（[apps/kafka/consumer.go:16](../apps/kafka/consumer.go#L16)）ごとに独立したオフセットを持つ。したがって group を分ければ同じログを何系統でも全件読めるし、オフセットを先頭に巻き戻せば過去のレコードを再消費（リプレイ）できる。Kafka では `--from-beginning` が先頭オフセットからの読み直しを指定し（[apps/kafka/consumer.go:27](../apps/kafka/consumer.go#L27)）、`make demo-kafka-replay`（[Makefile:49](../Makefile#L49)）が「再 produce せずに新しい group 名で過去レコードだけを読み直す」リプレイを実演する。Kinesis も同様に、コンシューマが shard iterator を `TRIM_HORIZON`（先頭）か `LATEST`（末尾）で取得して位置を自分で管理する（[apps/kinesis/consumer.go:17](../apps/kinesis/consumer.go#L17), [apps/kinesis/consumer.go:32](../apps/kinesis/consumer.go#L32)）。

なお queue でも「fan-out」自体は可能である。ActiveMQ は宛先を `/queue/orders`（競合）と `/topic/orders`（購読者全員に配る）で切り替えられ（[apps/activemq/main.go:29](../apps/activemq/main.go#L29)）、`make demo-activemq-topic`（[Makefile:33](../Makefile#L33)）は 2 購読者が同じ 3 通をそれぞれ受け取る fan-out を見せる。ただしこれは「購読者がその瞬間に繋がっていること」が前提のブローカー側 pub/sub であり、後から参加した系が過去のメッセージを読み直せる stream の fan-out とは性質が異なる。queue の競合は `make demo-sqs`、stream のリプレイは `make demo-kafka-replay` で対比しながら手を動かすと、この差が体感できる。

## 5. 配信保証と冪等性

非同期メッセージングの配信保証は、伝統的に 3 段階で語られる。

- **at-most-once（高々 1 回）**: メッセージは失われることはあっても、重複することはない。送りっぱなしで再送しない設計。取りこぼしを許せる場合に限る。
- **at-least-once（少なくとも 1 回）**: メッセージは重複することはあっても、失われることはない。ACK が届かなければ再送するため、同じメッセージが 2 回以上届きうる。
- **exactly-once（ちょうど 1 回）**: 失われも重複もしない理想。実現には送受信の両端とブローカーにまたがる協調（トランザクション・冪等プロデューサ・重複排除）が必要で、コストが高い。

重要なのは、**本章で扱う 4 ミドルウェア（SQS / ActiveMQ / Kafka / Kinesis）は、実用上いずれも at-least-once として扱うのが安全** という点である。ネットワーク断・コンシューマのクラッシュ・ACK / オフセットコミットのタイミングずれといった要因で、同じメッセージが再配信されうる。Kafka にはトランザクション機構があり「Kafka 内で閉じた exactly-once」は構成できるが、外部の DB やメール送信まで含めた end-to-end の exactly-once は保証されない。したがって設計の前提はつねに at-least-once、すなわち **「同じメッセージが 2 回来ても結果が壊れないコンシューマ（冪等な消費）を書くこと」が非同期設計の必須要件** になる。冪等化の典型は、メッセージ ID をキーにした重複排除（処理済みなら二度目はスキップ）や、`UPSERT` のように何度実行しても同じ状態に収束する操作を使うことである。

再配信が実際に起きる様子は SQS の DLQ デモで観察できる。本体キューは可視性タイムアウト 5 秒（[localstack-init/init-aws.sh:11](../localstack-init/init-aws.sh#L11)）と `maxReceiveCount=2` の RedrivePolicy（[localstack-init/init-aws.sh:12](../localstack-init/init-aws.sh#L12)）で構成されており、`make demo-sqs-dlq`（[Makefile:16](../Makefile#L16)）は「削除せずに受信 → 可視性タイムアウトで再表示 → また削除せず受信」を繰り返す。デモの受信回数の推移は次のとおり。

```
produce 1 通
  │
  ├ consume --no-delete            → receiveCount=1（ACK せず放置）
  │    …可視性タイムアウト 5s 経過で再び見えるようになる
  ├ consume --no-delete            → receiveCount=2
  │    …再びタイムアウト経過
  ├ consume（3 回目の受信試行）      → maxReceiveCount=2 超過 → 本体キューは空、DLQ へ移送
  │
  └ consume --queue orders-dlq     → receiveCount=3（累積値・リセットされない）
```

コンシューマは受信のたびに `ApproximateReceiveCount` を要求し（[apps/sqs/consumer.go:35](../apps/sqs/consumer.go#L35)）、その値を表示する（[apps/sqs/consumer.go:46](../apps/sqs/consumer.go#L46)）。1 回目は `receiveCount=1`、2 回目は `receiveCount=2`、そして 3 回目の受信試行で `maxReceiveCount=2` を超えるため、メッセージは本体キューには配信されず DLQ（`orders-dlq`）へ移送される。

ここで押さえておきたい実測事実として、**`ApproximateReceiveCount` は累積値であり、DLQ へ移動しても 0 にリセットされない**。DLQ に移った後にそのキューから読むと、メッセージは `receiveCount=3` を保ったまま現れる。「DLQ に入った = これまで何回配信を試みたか」の情報が失われないため、リトライ回数を根拠にした調査や再処理の判断がしやすい。この挙動は再配信と冪等性が「概念」ではなく実際にコードとインフラ設定の上で起きていることを示す好例である。

## 6. 本章 5 サービスのマッピング

最後に、本章で登場する 5 つのサービスを queue / stream の軸とマネージド / セルフホストの軸で位置づける。ハンズオンのコードがあるのは前半 4 つ、Firehose のみコンセプト解説のみとなる。

| サービス | 分類 | 運用形態 | 本章での扱い |
|----------|------|----------|--------------|
| SQS | queue | マネージド（AWS） | ハンズオン + DLQ / 可視性タイムアウトのデモ |
| ActiveMQ | queue（broker 型 MQ） | セルフホスト | ハンズオン + queue / topic 切替の fan-out デモ |
| Kafka | stream | セルフホスト | ハンズオン + consumer group リプレイのデモ |
| Kinesis Data Streams | stream | マネージド（AWS） | ハンズオン + shard iterator のデモ |
| Kinesis Data Firehose | stream 配送サービス | マネージド（AWS） | コンセプトのみ（consumer コードを書かない） |

SQS と ActiveMQ は同じ queue でも立ち位置が違う。SQS は AWS が運用を肩代わりするマネージドサービスで、ブローカーの冗長化やスケールを意識しなくてよい代わりに STOMP のような topic pub/sub は素直には持たない。ActiveMQ は自分で立てる broker 型 MQ で、`/queue`（競合）と `/topic`（fan-out）を宛先で切り替えられる柔軟さがある反面、可用性は自分で担保する。Kafka と Kinesis も同じ stream ながら、Kafka はセルフホストで partition / consumer group を自分で設計し、Kinesis はマネージドで shard 単位のスループット管理が中心になる。Firehose は「stream を受けて S3 などへバッチ配送する」専用サービスで、自前の consumer ループを書かないため本章ではコードを持たず、位置づけの解説にとどめる。

このマッピングを地図として、以降のドキュメントで各サービスのコードに降りていく。読み進めの案内は次のとおり。

- `02_sqs.md` — マネージド queue の消費ループ、可視性タイムアウト、DLQ（本章デモの詳細）
- `03_activemq.md` — STOMP による queue（競合）と topic（fan-out）の切替
- `04_kafka.md` — consumer group とオフセット、`--from-beginning` によるリプレイ
- `05_kinesis.md` — shard と iterator（`TRIM_HORIZON` / `LATEST`）の自前管理
- `06_firehose.md` — consumer を書かない配送サービスとしての Firehose
- `07_selection_guide.md` — 料金・運用・要件から 5 サービスをどう選ぶか

まずは本章の軸である「queue は配って消す / stream は追記して残す」「実用上は at-least-once なので冪等に消費する」という 2 点を頭に置いたうえで、`02_sqs.md` から手を動かしていくとよい。

# サービス分割の考え方

> マイクロサービスで最も難しく、最もやり直しが効きにくいのが「どこで線を引くか」である。本章では DDD の境界づけられたコンテキストとビジネス能力の 2 つのアプローチを概観し、EC ドメインへの適用と、本サンプルが採用した 5 サービス分割の理由を示す。

---

## 1. なぜ サービス分割 を扱うのか

マイクロサービスのメリット — 独立デプロイ、独立スケール、障害分離 — は「線の引き方が妥当である」ことを前提に成立する。逆に言えば、分割が不適切だと、独立デプロイのつもりが他サービスの変更とほぼ常に同期リリースになる、独立スケールのつもりが結局すべてが等しく重くなる、といった現象が起きる。

線の引き方を誤ると、コードは複数リポジトリに散らばっているのに、変更の波及はモノリス時代より広がる、という最悪の結果になる。「分散モノリス」と呼ばれる失敗形態である。

そのため、本章で実装の話に入る前に、分割の判断軸を 1 つの doc で固めておく。Conway's law が「組織構造がアーキテクチャを規定する」と教えてくれたあとに来るべき問いは、「では、どのような単位で組織とサービスを切るか」である。これは技術ではなくドメインの問題であり、設計の出発点はドメインの理解にある。

## 2. サービス分割 とは

分割の議論には大きく 2 つの系譜がある。

### 2.1 DDD: 境界づけられたコンテキスト

ドメイン駆動設計が提唱する **境界づけられたコンテキスト**（Bounded Context）は、「ある業務用語・モデルが一貫した意味を持つ範囲」を 1 単位とする考え方である。同じ「商品」という単語でも、カタログ部門にとっては「顧客に見せる表示用情報」であり、在庫部門にとっては「物理的に倉庫にある数量の真実」である。これらは表面的には同じ「商品」だが、関心も生存期間も更新頻度も違う。同じモデルで扱おうとすると、どちらの関心も中途半端に取り込んだ巨大エンティティが生まれる。

境界づけられたコンテキストは、この「文脈ごとにモデルを分ける」線引きを正当化する。結果としてサービス境界の有力候補になる。

### 2.2 ビジネス能力（Business Capability）

もう 1 つは、組織が顧客に提供している **能力** を 1 単位とする見方である。EC なら「商品を見せる能力」「在庫を持つ能力」「注文を受ける能力」「決済する能力」「ユーザを認証する能力」が能力の例になる。能力は組織図にも反映されやすく、Conway's law と相性が良い。

DDD の境界づけられたコンテキストとビジネス能力は、出発点こそ違うが（前者はモデルから、後者は組織・業務から）、最終的に引かれる線は概ね一致することが多い。両者は対立する選択肢ではなく、同じ線を別角度から検証する道具と捉えるとよい。

### 2.3 「同じ用語が違う意味を持つ」現象

分割を進めると必ず出会うのが、**同じ名前のエンティティが別サービスで別の意味を持つ** 現象である。EC の `product_id` は典型で、

- カタログでは「顧客に見せる名前・説明・価格・画像 URL の主体」
- 在庫では「倉庫にいくつあるか・予約済みがいくつかを記録する主体」
- 注文では「過去のある時点で価格を確定して買われた商品の参照」

と、サービスごとに「product とは何か」の答えが違う。これはバグではなく **意図的な重複** であり、境界づけられたコンテキストが正しく機能している証拠である。共通の `products` テーブルを 1 つ作って共有しようとすると、再びモノリス的結合が戻ってくる。

### 2.4 分割の粒度: 2 つの典型的な失敗

| 失敗 | 症状 | 原因 |
|---|---|---|
| 分割しすぎる | 1 リクエストで 7〜8 サービスを呼ぶ。観測性なしでは追えない。あるユースケースの変更が常に複数サービスをまたぐ | ドメインの自然な単位より細かく切った（例: User と Profile を別サービスに） |
| 分割しなさすぎる | 1 サービスが複数の意思決定主体（チーム）から同時に変更される。リリース調整会議が増える | ビジネス能力の境界を無視して「とりあえず大きく」切った |

「分割しすぎる」失敗は派手で目立つが、実害が大きいのはむしろ「分割しなさすぎる」側で、Conway's law に逆らった組織と擦り合わせるコストが恒常的にのしかかる。最初は **大きめに切ってあとで割る** のが安全側の戦略になる。モジュラーモノリスから始めて段階的にマイクロサービス化する流派は、この洞察に立脚している。

## 3. 実例: 本章のサンプルではどう現れるか

### 3.1 EC ドメイン分割の選択肢

EC で考えられる分割候補は多い。

- catalog（商品マスタ）
- inventory（在庫）
- order（注文）
- payment（決済）
- user-auth（ユーザ・認証）
- cart（カート）
- shipping（配送）
- pricing（価格決定・キャンペーン）
- recommendation（推薦）
- review（レビュー）
- notification（メール・プッシュ通知）

教材として全てを実装すると、レジリエンスや観測性の本筋がぼやける。本章は **5 サービス + BFF** に絞る。cart はフロント側 state（localStorage）に閉じ、shipping / pricing / recommendation / review / notification は今回扱わない。これは「分割しすぎない」原則を教材自身が実践した結果である。

### 3.2 採用した 5 サービスの責務

| サービス | 責務 | 所有データ |
|---|---|---|
| **catalog** | 商品マスタ・表示用情報。顧客に見せる名前・説明・価格 | `products(id, name, price, ...)` |
| **inventory** | 在庫の真実。予約・確定・解放のライフサイクル | `stocks(product_id, available, reserved)`, `reservations(id, order_id, ...)` |
| **order** | 注文ライフサイクル。Saga を駆動する主役 | `orders(id, user_id, status, ...)`, `order_items(...)`, `saga_log(...)` |
| **payment** | 決済の試行と結果。意図的に時々失敗する | `payments(id, order_id, status, amount, ...)` |
| **user-auth** | ユーザ管理と JWT の発行・検証 | `users(id, email, password_hash, ...)` |

BFF はこの 5 サービスに対する集約点であり、REST から gRPC への変換と、UI 向けの応答整形を担う。BFF は永続化を持たない。

### 3.3 「同じ product_id を別の意味で扱う」が現れる場所

`catalog` と `inventory` はいずれも `product_id` をキーにレコードを持つが、意味は異なる。

- `catalog` の `products(id, name, price)` は **表示用の真実**。顧客が画面で見る情報の出所はここ。
- `inventory` の `stocks(product_id, available, reserved)` は **在庫の真実**。発注業務や倉庫運用が触る対象はこちら。

BFF が商品一覧を返すときは、`catalog.ListProducts` で表示用情報を取り、各 `product_id` について `inventory.GetStock` で在庫数を取り、UI 層で合成する。**1 つの DB に JOIN を投げて済ませない**。両者の更新頻度・更新者・障害ドメインは異なるので、結合は呼び出し側（BFF）で行うのが妥当である。

JWT 検証フローも分割を体現している。BFF の `bff/internal/middleware/auth.go::Auth` は受け取った Cookie の JWT を取り出し、`services/user-auth/internal/server/grpc.go::GetUser` を gRPC で呼んでユーザを解決する。BFF は JWT の構造を知らず、user-auth はトークン発行と検証（`services/user-auth/internal/jwt/jwt.go::Issue` / `Verify`）の所有者である。`bff/internal/handler/auth.go::Auth.Me` は、この境界を経由して「自分のユーザ情報を返す」という UI 向け能力を提供する。

## 4. 落とし穴 / よくある誤解

**「DRY のために共通エンティティを作る」**
カタログの `Product` と注文行の `OrderItem.product_snapshot` を「重複だから」と統一しようとすると、再び結合が戻る。注文行は注文時点の価格を保持するべきで、未来のカタログ価格変更に追従してはならない。重複に見えて意味が違う。

**「同じテーブルを 2 サービスで読むだけならよい」**
読むだけでも、片方のスキーマ変更がもう片方を壊す瞬間に独立デプロイは終わる。共有 DB は最も陰湿な結合である。`docs/06_data_ownership.md` で改めて扱う。

**「組織を無視して理想の分割を引ける」**
Conway's law は規範ではなく観察である。1 サービスを 2 チームで同時に触る運用は、ほぼ確実に破綻する。チーム単位と能力単位が一致するように分割する。

**「最初から細かく分けるほど将来が楽」**
逆である。境界の引き直しコストはサービス数の増加に伴って急上昇する。最初は粗く、ドメイン理解が深まってから割るのが定石。

## 5. スコープ外 — この章で扱わないこと

- **Event Storming の手順**: 境界づけられたコンテキストを発見するワークショップ手法は本書の範囲外。DDD 専門書に譲る。
- **DDD の他要素の網羅**: Aggregate, Entity, Value Object, Domain Event, Repository などの戦術的 DDD は扱わない。本章は分割の境界（戦略的 DDD のごく一部）にのみ焦点を当てる。
- **境界の引き直し（マイグレーション）手法**: 既存モノリスをサービスに分けていく Strangler Fig などのリファクタリング技法は扱わない。
- **データ所有の詳細**: 分割と切り離せないテーマだが、独立した重要トピックとして `docs/06_data_ownership.md` で扱う。
- **通信プロトコルの選択**: 分割した後の「どう繋ぐか」は次章 `05_communication.md` で扱う。

# 03_udp_basics: UDP の正体

UDP は「メッセージをそのまま投げつける」L4 プロトコルである。udp-echo サーバーは TCP との差異を裸で観察するための最小実装として設計されている。

---

## 1. UDP の正体

UDP（User Datagram Protocol）の本質的な性質を一言ずつまとめる：

- **データグラム**：送受信の単位が「1 回の送信＝1 つのメッセージ（データグラム）」。TCP のようにストリームとして流れるのではなく、各 `sendto` が独立したパケットになる。
- **接続なし**：SYN/SYN-ACK/ACK のハンドシェイクがない。送りたいときに送るだけ。サーバーへの「接続」という概念がなく、送信先アドレスを毎回指定する。
- **順序なし**：複数のデータグラムが異なるルートを通ることがあり、到着順が送信順と一致しない場合がある。TCP のような並べ直しを OS が行わない。
- **ロス可**：ネットワークの輻輳やルータのバッファ溢れでパケットが消える。再送は行われない。アプリケーションが再送を実装しない限り、そのまま消失する。
- **境界保持**：`sendto(5000 bytes)` で送ったら `recvfrom` で 5000 バイトがまとめて届く（MTU 以内であれば）。TCP とは逆に、メッセージ境界が維持される。

---

## 2. TCP との対比表

| 比較項目 | TCP | UDP |
|----------|-----|-----|
| 通信単位 | バイトストリーム（境界なし） | データグラム（境界あり） |
| 接続 | 必要（3-way handshake） | 不要（connectionless） |
| 順序保証 | あり（シーケンス番号） | なし |
| 再送 | OS が自動で行う | なし（アプリ責務） |
| ロス検知 | OS が行う（ACK タイムアウト） | アプリが行う（またはしない） |
| レイテンシ | ハンドシェイク＋再送コストあり | 低い（投げっぱなし） |
| オーバーヘッド | ヘッダ 20〜60 バイト | ヘッダ 8 バイト |
| Go の型 | `net.Conn`（`net.Listen` + `Accept`） | `net.PacketConn`（`net.ListenPacket`） |
| 適した用途 | HTTP・SSH・DB プロトコル等 | DNS・QUIC・リアルタイムゲーム等 |

## 3. servers/udp-echo/ コードウォークスルー

### NewServer

[servers/udp-echo/server.go:14](../servers/udp-echo/server.go#L14)

```go
func NewServer(pc net.PacketConn) *Server {
    return &Server{pc: pc, log: slog.Default()}
}
```

TCP の `net.Listener` に相当するのが UDP では `net.PacketConn` である。`main.go` で `net.ListenPacket("udp", ":9002")` を呼んで（[servers/udp-echo/main.go:17](../servers/udp-echo/main.go#L17)）、その戻り値を注入している。

### Serve — 単一ゴルーチンがなぜ自然か

[servers/udp-echo/server.go:18](../servers/udp-echo/server.go#L18)

```go
func (s *Server) Serve() error {
    buf := make([]byte, 65536)
    for {
        n, addr, err := s.pc.ReadFrom(buf)
        if err != nil {
            if errors.Is(err, net.ErrClosed) {
                return nil
            }
            return err
        }
        s.log.Info("read", "n", n, "from", addr.String())
        if _, werr := s.pc.WriteTo(buf[:n], addr); werr != nil {
            s.log.Error("write_err", "err", werr.Error())
        }
    }
}
```

TCP サーバーでは `Accept()` するたびに `net.Conn` が生まれ、それぞれ別ゴルーチンで `handle` を動かすのが自然だった。UDP にはそもそも「接続」がないため `Accept` に相当するものがない。`ReadFrom` は 1 回の呼び出しで「どこから来たか（`addr`）」と「何バイト届いたか（`n`）」を同時に返す。エコーするには `addr` 宛に `WriteTo` するだけでよい。

接続ごとにステートを持つ必要がなく、ひとつのバッファで全クライアントを順番に捌ける。UDP エコーは本質的に stateless（1 データグラムで完結）なので、シングルゴルーチンのループが最もシンプルかつ正しい実装になる。

## 4. TCP と同じ長文を送る実験

UDP の「境界保持」を実際に観察する実験手順：

```bash
# ターミナル 1: サーバー起動
cd servers/udp-echo && go run .

# ターミナル 2: 長い文字列を送信（MTU 内、約 1400 バイト以内）
python3 -c "print('A' * 1000, end='')" | nc -u -w1 localhost 9002

# 大きめのメッセージ（フラグメント領域）
python3 -c "print('B' * 8000, end='')" | nc -u -w1 localhost 9002
```

サーバー側のログには `read n=1000` や `read n=8000` のように **1 行だけ** 出る。TCP と違って `ReadFrom` が複数回に分かれることはない（カーネルがデータグラム全体をバッファに溜めてから返すため）。これが「メッセージ境界が保持される」という意味である。

TCP で同じことをやると `read n=4096` / `read n=3904` のように分割されて届く場合があった。この差こそが「ストリーム vs データグラム」の実体である。

## 5. MTU / フラグメンテーション / 65507 バイト上限

```
Ethernet フレーム上限: 1500 バイト（MTU）
  └─ IP ヘッダ: 20 バイト
  └─ UDP ヘッダ: 8 バイト
  └─ UDP ペイロード: 最大 1472 バイト（フラグメントなし）
```

UDP データグラムは理論上 65535 バイト（IP パケット上限）まで送れるが、UDP ヘッダ 8 バイト + IP ヘッダ 20 バイトを引くと **65507 バイト** がアプリケーションで使える上限になる。`servers/udp-echo/server.go:19` でバッファを `65536` バイトに設定しているのはこのためである。

Ethernet の MTU（1500 バイト）を超えるデータグラムは IP レベルでフラグメント（断片化）される。フラグメントはルータの中間経路で再組み立てされるが、途中のフラグメントが 1 つでも失われるとデータグラム全体が廃棄される。実用上は **1472 バイト以内**（Ethernet MTU 内）に収めるか、PMTUD（Path MTU Discovery）で安全なサイズを動的に調べるのが推奨される。DNS は 512 バイト（UDP）または TCP フォールバックという設計でこの問題を回避している。

## 6. 落とし穴

### ロス検知不能

UDP では送ったデータが届いたかどうかをアプリが知る手段がない。`WriteTo` がエラーを返さなくてもパケットがルータで廃棄されることがある。重要なデータを送るなら、アプリ側でタイムアウト＋再送、または受信確認（ACK 相当）を自前で実装する必要がある。DNS がこれをどう扱うかは `05_dns.md` を参照。

### 順序入れ替わり

複数のデータグラムを素早く送ると、到着順が送信順と異なることがある。シーケンス番号をペイロードに埋め込んで受信側で並べ直すか、順序に依存しないプロトコル設計にする必要がある。LPP（[servers/lpp/](../servers/lpp/)）は TCP 上に実装されているため順序問題を意識しなくてよいが、UDP 上に同等の機能を作る場合はこの問題が浮上する。

### 再送はアプリ責務

「届かないかもしれないが、届けば速い」のが UDP の設計思想である。リトライロジック・タイムアウト・指数バックオフはすべてアプリケーション層で実装する。QUIC（HTTP/3 の下位層）はこれを UDP の上に実装した例であり、「TCP の信頼性を UDP の上で再発明した」プロトコルとも言える。

## 7. L4 のみであることを明示

素の UDP echo サーバーも L4 だけの世界である。L5（セッション・TXID などによる問い合わせ対応）・L6（バイト列の構造定義）・L7（アプリケーションとしての意味）を一切持たない。受け取ったバイト列をそのまま送り返すだけで、「何が届いたか」にサーバーは無関心だ。後続章では、この同じ UDP ソケットの上に DNS（`05_dns.md`）がどう積み上がるかを見ていく。DNS は TXID という L5 的な仕組みでリクエストとレスポンスを対応づけ、QNAME ラベル符号化という L6 的なバイト変換を行い、A レコード応答という L7 的なアプリ意味を付与する。udp-echo との差分を見ると、「L5/L6/L7 を追加するとは何をコードに足すことか」が具体的に分かる。

## 8. まとめ / 関連 doc / この先の話題

### まとめ

UDP はデータグラム・接続なし・順序なし・ロス可・境界保持という性質を持つ L4 プロトコルである。TCP と違ってストリームではないため、受信側でメッセージを再構成する必要がない一方、信頼性はアプリ側が担う。udp-echo の `ReadFrom` / `WriteTo` による単一ゴルーチン実装は、UDP の stateless な性質を素直に反映している。MTU を意識した設計と再送ロジックの不在が、UDP を使うアプリの主要な設計課題になる。

# トークン運用の実務

## 1. 概要

JWTを「発行して終わり」にはできない。実運用では以下の問いに答えなければならない。

- **漏洩したトークンをどう無効化するか？** — JWTはステートレスなため署名さえ通れば有効と判定される。発行後に取り消す仕組みが別途必要。
- **有効期限はどう設計するか？** — 長すぎれば漏洩リスクが高く、短すぎれば頻繁な再ログインを強いる。
- **ブラウザのどこに保存するか？** — XSSとCSRFは保管場所によってリスクが逆転する。
- **鍵を更新するとどうなるか？** — 鍵ローテーション中に既存トークンを壊さない方法が必要。

本章はこれらの実務論点を体系化する。デモは `02_jwt.md` と同じ JWTサーバ(`make jwt` / `http://localhost:9001`)、コードは `09_authn_authz/jwt/` を参照する。

## 2. access + refresh の設計

### なぜ2種類のトークンを使うか

アクセストークン1本だけにすると、有効期限を長くするほど漏洩時の被害期間が伸びる。かといって短くすると、期限切れのたびに再ログインが必要になる。これを解決するのが**短命アクセストークン + 長命リフレッシュトークン**の組み合わせ。

| 種別 | 役割 | TTLの目安 |
|------|------|-----------|
| アクセストークン | APIアクセスの認証 | 5〜15分 |
| リフレッシュトークン | アクセストークンの再取得 | 1〜30日(用途による) |

TTLの目安は用途に応じて調整する。金融・医療など高リスク用途では短め(accessを5分、refreshを数時間)、一般的なSaaSでは長め(accessを15分、refreshを7〜30日)が多い。

### ライフサイクル

```
クライアント                            サーバ
    |                                     |
    |-- POST /login ─────────────────────>|
    |<── { access(5分), refresh(24h) } ───|
    |                                     |
    |-- GET /api  Bearer: access ────────>|  署名検証 + exp確認のみ(ストア不要)
    |<── 200 data ────────────────────────|
    |                                     |
    |  (5分経過)                          |
    |                                     |
    |-- POST /refresh  Bearer: refresh ──>|  refresh検証 + blocklist確認
    |<── { new_access(5分), new_refresh } |  旧refresh → blocklist
    |                                     |
    |-- POST /logout  Bearer: refresh ───>|  refresh jti → blocklist
    |<── 200 ─────────────────────────────|
    |                                     |
    |  access(5分)が切れれば全セッション終了
```

### 責務分担

- **アクセストークン検証**: サーバは署名と `exp` を確認するだけ。ストアアクセス不要。高速でスケールしやすい。
- **リフレッシュトークン検証**: blocklist照会が伴う。アクセストークンより発行頻度が低いため許容できる。
- **ログアウト・強制失効**: リフレッシュトークンをblocklist登録するだけでセッションを実質終了できる。

## 3. 失効(revocation)戦略

JWTはステートレスなため「サーバが発行済みトークンを覚えていない」。漏洩や強制ログアウトで即時失効させたい場合、何らかの仕組みが必要。主な戦略を比較する。

### 戦略比較表

| 戦略 | 概要 | アクセスの即時失効 | ストート状態 | 実装コスト |
|------|----|:-----------:|:----------:|:--------:|
| **(a) 短命access + refreshのみ失効** | accessは短命(5分)で自然失効を待つ。refreshだけblocklist管理 | △ 最大TTL分だけ遅延 | 小(refreshのみ) | 低 |
| **(b) accessもblocklist(jti)で失効** | accessのjtiもblocklist登録し即時失効 | ◎ 即時 | 大(全アクセスjti) | 中〜高 |
| **(c) トークンバージョニング** | ユーザにversionフィールドを持たせ、強制失効時にインクリメント。access内のversionと照合 | ◯ 全デバイス一斉失効 | 中(userテーブル1カラム) | 中 |

#### (a) 短命access + refreshのみ失効

最もシンプル。デモ(`09_authn_authz/jwt/blocklist.go`)もこの方式にリフレッシュローテーションを加えたもの。

- 漏洩したアクセストークンは最大5分間有効のまま。
- ほとんどのWebサービスはこの許容範囲を受け入れている。

#### (b) jti blocklist でアクセスも即時失効

```
// POST /admin/revoke-access でaccessのjtiをblocklist登録
blocklist.Revoke(accessClaims.ID)
```

- 要求: `/api` リクエストごとにblocklist照会が走る。高トラフィックではRedisのルックアップが全リクエストに加わる。
- 利点: 即時失効が確実。不正アクセスの検知後すぐに対応できる。
- ストアが肥大化する問題: エントリにTTL(=accessの`exp`)を設定して自動削除する(Redisなら`SETEX`)。

#### (c) トークンバージョニング

```
// userテーブルにtoken_versionカラム
// アクセストークンのpayloadにtoken_version埋め込み
// /api ミドルウェアでDB or cacheと照合
if claims.TokenVersion != user.TokenVersion {
    return 401
}
```

- 全デバイスの一斉強制ログアウトが簡単(versionをインクリメントするだけ)。
- パスワード変更・アカウント停止時に有効。
- ユーザごとのversion取得がリクエストごとに必要(キャッシュ推奨)。

### トレードオフまとめ

```
即時性    低 ←────────────────────────────→ 高
          (a)短命access     (c)バージョニング     (b)jti blocklist

性能コスト 低 ←────────────────────────────→ 高
          (a)              (c) ※キャッシュ可    (b) 全リクエストにlookup

ストア量  小 ←────────────────────────────→ 大
          (a) refreshのみ  (c) userカラム1本    (b) 全access jti
```

## 4. リフレッシュトークンローテーション

### 仕組み

リフレッシュトークンを**使い捨て**にする。`POST /refresh` を呼ぶたびに旧トークンを無効化し、新しいペアを返す。

```
クライアント                              サーバ
    |                                      |
    |-- POST /refresh  Bearer: refresh_A ->|
    |                                      | 1. refresh_Aを検証
    |                                      | 2. refresh_A の jti → blocklist
    |<── { access_B, refresh_B } ──────────| 3. 新ペアを発行
    |                                      |
    |  (refresh_Aが盗まれていた場合)        |
    |                                      |
    |  攻撃者: POST /refresh  Bearer: refresh_A
    |                                      | → blocklist hit → 401
```

### 再利用検知(reuse detection)

正規クライアントは常に最新のリフレッシュトークンを使う。もし**失効済みの**リフレッシュトークンで `/refresh` が来たら、以前のトークンが盗まれて使われたと判断できる。

```
クライアント(正規)    攻撃者              サーバ
      |                  |                  |
      |                  |                  | refresh_Aを発行済み
      |-- /refresh A --->|                  |
      |  (通信を傍受)     |                  |
      |                  |-- /refresh A --->| blocklist: refresh_A を登録
      |<── { B } ────────|                  | ← 攻撃者が先にローテーション
      |                  |                  |
      |-- /refresh A --->|                  | ← 正規クライアントが旧Aで試行
      |                  |             401  | blocklist hit → 侵害を検知
      |<── 401 ──────────|                  | → 全リフレッシュトークンを無効化(推奨)
```

再利用検知時に**そのユーザの全セッションを強制失効**させると、攻撃者が取得したトークンも一掃できる。

デモでの実装(`09_authn_authz/jwt/handlers.go`):

```go
// 古いリフレッシュトークンのJTIをblocklist登録してから新しいペアを発行
blocklist.Revoke(claims.ID)
access, refresh, err := issueTokenPair(signer, claims.Subject)
```

> **注:** デモはインメモリblocklist。サーバ再起動で失効リストが消える。本番はRedis等の共有ストアを使うこと。

## 5. トークンの保存場所(ブラウザ)

ブラウザでトークンを扱う場所として主に3つある。それぞれXSS・CSRFへの耐性が異なる。

### 保管場所の比較表

| 保管場所 | XSS耐性 | CSRF耐性 | SPA利便性 | 主な用途 |
|----------|:-------:|:--------:|:---------:|---------|
| **HttpOnly Cookie** | ◎ JSからアクセス不可 | △ SameSite=Strict/LaxかCSRFトークンが必要 | △ Cookieを自動送信 | 一般的な推奨 |
| **localStorage** | ✗ JSから読み書き可 | ◎ 自動送信されない | ◯ Authorization headerで送信 | 非推奨(XSSで即漏洩) |
| **sessionStorage** | ✗ JSから読み書き可 | ◎ 自動送信されない | ◯ | タブ閉じで消える。XSSは防げない |
| **メモリ(JS変数)** | △ XSSで盗めないがタブ間共有不可 | ◎ | △ ページリロードで消える | SPA + BFF構成の内部 |

### HttpOnly Cookie の留意点

```
Set-Cookie: refresh_token=<value>;
  HttpOnly;       ← JSから読めない(XSSで盗めない)
  Secure;         ← HTTPS接続のみ送信
  SameSite=Strict ← 他サイトからのリクエストに付かない(CSRF対策)
  Path=/refresh;  ← リフレッシュエンドポイントのみに限定
  Max-Age=86400
```

- `SameSite=Strict` はクロスオリジンナビゲーション(メール内リンクなど)にも Cookie を付けないため、ユーザビリティに影響することがある。`SameSite=Lax` との使い分けを検討する。
- アクセストークンをHttpOnly Cookieに入れると、JavaScriptからBearer headerとして送信できなくなる。BFF(Backend for Frontend)パターンでサーバ側でCookieをheaderに変換する構成が一般的。

### CSRF・XSSの詳細対策

`03_security_measures` を参照。本章はトークン保管の選択肢に絞る。

## 6. その他の実務論点

### 鍵ローテーション(kid / JWKS)

署名鍵を定期的に交換する必要がある。JWTの `kid`(Key ID)ヘッダーを使うと、複数の鍵を同時に有効にしながら段階的に移行できる。

```
// 新鍵 kid=v2 で発行
Header: { "alg": "RS256", "kid": "v2" }

// 検証側: JWKSエンドポイントからkidに対応する公開鍵を取得
GET /.well-known/jwks.json
→ { "keys": [ {"kid":"v1",...}, {"kid":"v2",...} ] }
```

ローテーション手順:
1. 新しい鍵ペア(kid=v2)を生成し、JWKSに追加。
2. しばらく v1・v2 両方で発行・検証を受け付ける(既存v1トークンのTTLが切れるまで)。
3. v1をJWKSから削除。

デモでは起動時に `rsa.GenerateKey` で1回生成するのみ(`09_authn_authz/jwt/signer.go`)。マルチキーのJWKSは本章の発展課題として `07_api_m2m.md` でも触れられている。

### 標準クレームの検証

JWTを受け取ったときに検証すべきクレーム:

| クレーム | 意味 | 検証内容 |
|----------|------|---------|
| `exp` | 有効期限(Unix秒) | 現在時刻 < exp |
| `nbf` | 有効開始時刻 | 現在時刻 >= nbf |
| `iss` | 発行者 | 期待する発行者と一致するか |
| `aud` | 対象者 | このサービスが対象に含まれるか |
| `sub` | 主体(ユーザID) | 存在するユーザか |
| `jti` | トークンID | blocklist未登録か |

`aud` の検証を省略すると、他サービス向けのトークンで自サービスに侵入できる(混乱した代理問題)。

### クロックスキュー

分散システムではサーバ間の時計がわずかにズレる。`exp` の判定を厳密にしすぎると正当なトークンを弾いてしまう。一般的に **60秒程度の許容(leeway)** を設定する。

```go
// github.com/golang-jwt/jwt/v5 での設定例
parser := jwt.NewParser(
    jwt.WithLeeway(60 * time.Second),
)
```

### トークンサイズ

JWTはペイロードにクレームを詰めるほど大きくなる。Cookie制限(通常4KB)、HTTP header制限、ネットワーク帯域を考慮する。

- アクセストークンには最小限のクレームだけ入れる(`sub`, `exp`, `iat`, `jti`, `token_type`)。
- ロール・権限情報は必要最小限に。大きなリストはDBルックアップに切り出す。
- 不要なクレームを追加しない。Payloadはbase64デコードで丸見えなので機密情報は禁止。

## 7. まとめ

### 推奨デフォルト構成

```
┌─────────────────────────────────────────────────┐
│ 推奨デフォルト                                   │
│                                                  │
│  アクセストークン: 5〜15分 TTL                   │
│  リフレッシュトークン: ローテーション有           │
│  保管: HttpOnly + Secure + SameSite Cookie       │
│  失効: リフレッシュblocklist のみ(戦略a)         │
│                                                  │
│  高リスク操作(パスワード変更・送金など)にのみ    │
│  アクセスblocklist(戦略b) or step-up authを追加  │
└─────────────────────────────────────────────────┘
```

| 要件 | 推奨 |
|------|------|
| デフォルト失効戦略 | (a) 短命access + refreshのみblocklist |
| 即時全デバイス失効が必要 | (c) トークンバージョニング を追加 |
| 高リスク操作の即時失効 | (b) jti blocklist をその操作のみに限定 |
| 鍵管理 | kid + JWKS で段階的ローテーション |
| ブラウザ保管 | HttpOnly Cookie (SameSite=Strict/Lax + Secure) |
| クロックスキュー | 60秒のleewayを許容 |

### ポイントの振り返り

- **accessは短命・refreshは長命**: 利便性と漏洩リスクのバランスを取る基本設計。
- **ローテーションで漏洩を検知**: 使い捨てrefreshは、再利用されたとき「誰かに盗まれた」とわかる唯一の手がかり。
- **失効戦略はコストと即時性のトレードオフ**: 全リクエストにblocklist照会を強要せず、リスクに応じて戦略を使い分ける。
- **HttpOnly Cookieがデフォルト**: XSSでトークンが盗まれるリスクを大きく下げられる。CSRFはSameSiteで緩和。
- **標準クレームを全て検証する**: 特に `aud` の省略は見落とされやすいが重大な穴になる。
